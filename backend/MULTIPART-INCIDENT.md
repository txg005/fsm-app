# Photo upload MALFORMED_REQUEST: proved and fixed server-side

Runtime fix commit: `cf0c5c8c7b806a372969c63f4c714f102636983b`, PR #2,
`feature/backend-mvp`. No main merge, Android edit, API change, migration, or
credential change. Existing APK can use the patched server.

## Reproduction, not inference

Serialized real Ktor **3.1.3** `MultiPartFormDataContent(formData {...})` using
exact Android Api.upload append types/headers: metadata String application/json,
file ByteArray image/jpeg with filename photo.jpg. Captured writeTo bytes show:

```text
Content-Disposition: form-data; name=metadata
Content-Type: application/json
Content-Length: 165

Content-Disposition: form-data; name=file; filename="photo.jpg"
Content-Type: image/jpeg
Content-Length: 631
```

These lengths belong to the synthetic frozen fixture, not user data. Boundary
termination is correct `--\r\n`; unquoted part names are valid. Prior server
whitelist rejected both legitimate Content-Length headers. Before the fix:
real-client parser test failed with MALFORMED_REQUEST; HTTP/real-PostgreSQL test
failed `expected201 / actual400`. These red runs were not counted as passes.

## Narrow fix and retained checks

Allow optional per-part Content-Length, **once**, case-insensitive. If present,
it must contain only ASCII digits, fit Long, and exactly match actual part-byte
length. Overall 11 MiB limit and file 10 MiB limit still use actual received bytes;
a declared length cannot bypass them. Duplicate/unknown headers remain rejected.
Exactly metadata then file, two parts, metadata limit/strict JSON, MIME/JPEG decode,
SHA/size verification, generated storage keys, and path traversal protections stay.
No general validation bypass or new wire field. Charset UTF-8, header case,
filename changes, malformed/mismatched/overflowing lengths, and duplicate lengths
are tested. Original hand-framed contract fixture without lengths still passes.

## Existing APK: recover the already-terminal FAILED queue

Old FAILED operations do not automatically retry merely because the server changed.
For the affected order, after API is healthy and network is available:

1. Open the affected order and choose **Исправить после окончательного отказа**.
2. Let the app load the fresh canonical server version; confirm it is ASSIGNED.
3. Choose **Вернуться к черновику, если сервер ASSIGNED**. It re-fetches and checks
   the shown version again. If version changed, review/reconfirm, not accept blindly.
4. Verify the preserved checklist/readings/comment/photo preview in the draft,
   then close again and start sending from the visible app if needed.

Static code review confirms returnToDraft transaction removes old terminal outbox
entries, preserves result/photo UUIDs and localPath, sets DRAFT with fresh revision.

reused. Do not choose Принять серверную or delete the draft/photo. If canonical is
CLOSED, unavailable, or refreshing fails, stop: keep the local copy, do not force
reclose or remove files. No promise of automatic recovery from an unknown outcome.
