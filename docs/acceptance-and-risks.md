## 1. Согласованный объём

Основание — TASK и AGENTS; уточнения пользователя из последнего поручения имеют приоритет над прежними предложениями этого review. Одобрены Kotlin/Compose/Room/Coroutines/Flow и Ktor/PostgreSQL/Docker Compose; уровень B с реальной offline-работой. Push и сложное разрешение конфликтов исключены.

Зафиксировано: demo accounts с одной ролью; заявки создаются только backend seeds; CRUD — локальные `inspection_results` до закрытия/синхронизации. Фото optional; GPS автоматически best effort при закрытии, отказ/timeout не теряет работу и не блокирует закрытие. `CLOSED` — финальное состояние. Конфликты явно показываются UI. Все entity/operation/log IDs — UUID String, включая служебные записи (UUID не заменяет проверку прав).

Простейший предлагаемый lifecycle: draft только локален; сервер незакрытые черновики не хранит; при закрытии обязательный durable Outbox. Архитектор фиксирует точный API/state contract. Обязательны `filesDir` + Room `localPath` + отдельный remote ref; `app_logs` + общий logger Log/DB + technical screen с bounded retention без секретов/PII. FGS не неубиваемый; WorkManager только дополнение. SDK и фактическое тестовое устройство ещё нужно назвать.

## 3. Минимальный lifecycle и безопасный sync

- `DRAFT` — локальный CRUD `inspection_results`, фотографии в `filesDir`; черновик не синхронизируется. Заявки/справочники только загружаются с backend seeds. Не строить обобщённую синхронизацию каждого редактирования.
- Close: завершить ограниченную по времени best-effort GPS-попытку, проверить обязательные предметные поля, затем **одной Room-транзакцией** сменить локальное состояние на close pending и записать durable Outbox operation. Нет окна «закрыто без операции». Все IDs сущностей, Outbox, log — UUID String; повтор использует тот же operationId и snapshot, не новый ID.
- Close pending заблокирован для редактирования/удаления; timeout/401/сеть сами по себе не доказывают, что сервер ничего не сделал. ACK переводит в финальный `CLOSED`; явная ошибка отображается UI. Возврат к редактированию после definitive rejection — только по контракту архитектора; нельзя менять snapshot существующего operationId и незаметно перезапускать close.
- Один сериализованный исполнитель на активный аккаунт. Очередь восстанавливается из Room после process death; нельзя оставить вечный in-flight. Сначала upload всех прикреплённых фото со стабильными UUID и сохранение remote refs; только затем close с этими refs. Фото optional, но неуспех upload выбранного фото нельзя молча превратить в close без фото. Сервер не хранит незакрытые inspection drafts; временные upload-объекты допустимы и требуют простого согласованного cleanup.
- Backend атомарно сохраняет эффект close и дедупликацию `(userId, operationId)` с unique constraint. Одинаковый ключ/payload — тот же результат; другой payload — ошибка. Фото upload также идемпотентен по стабильному photo ID. Повтор после server commit/потери ответа не создаёт второе выполнение/вложение. Не обещать сетевой exactly-once.
- `localPath` — локальный путь под контролем приложения в `filesDir`, не URL. Remote ref хранится отдельно и относится к аутентифицированному API; не принимать произвольный URL/path за доверенную ссылку, не открывать public-media доступ по знанию ID. Локальная копия не удаляется до ACK; без resumable chunks и внешнего object storage для MVP можно обойтись.
- Удаление draft: транзакционно удалить/пометить результат и связанные metadata, удалить только его неисполняемые операции/задачи; затем удалить файлы (Room и filesystem не имеют общей транзакции). Если файл остался после сбоя, безопасный retry cleanup удаляет orphan, но не восстанавливает draft. Запоздавший callback capture/upload должен проверить существование и состояние владельца и не upsert-ить удалённую запись. При штатном lifecycle до close операций вообще нет; проверить также stale/ошибочные pending-записи. Удаление close pending запрещено, пока не установлен однозначный исход close; `CLOSED` не удаляется через draft CRUD.
- Предлагаемый простой конфликт-контроль — revision + 409. Локальная копия сохраняется, UI явно показывает серверное изменение/финальный CLOSED; без автоматического обновления revision и перезаписи. Pull не стирает draft/pending и не воскрешает удалённый локальный черновик из кеша.
- Timeout/5xx — ограниченные безопасные retry с задержкой; 401 — вход заново, 403/400/413/409 — понятная ошибка, не бесконечный цикл. Ошибка одной заявки не должна блокировать остальные. Регистрация, сложные роли и refresh-token инфраструктура не требуются.
- Offline доступ к кэшу ранее вошедшего пользователя не означает актуальную проверку отзыва прав. Очередь привязана к аккаунту; повторный login того же владельца возобновляет отправку. Logout/switch не должен отправлять чужую очередь или незаметно удалять её; безопасный минимум — сохранить изолированную очередь и явно предупредить. Точное UX-правило фиксирует координатор.
- Logger — одна точка записи в Android Log и `app_logs`, одинаковая фильтрация без секретов/PII; bounded retention удаляет только старые logs, не pending Outbox. Technical screen показывает sync state и безопасные logs. Числовой предел retention — документированный implementation default, не отдельный бизнес-блокер.

## 5. Service: минимальный легитимный вариант и реальные ограничения

### Предложение: пользовательский SyncService (foreground, dataSync)

Кнопка «Отправить накопленные работы (включая фото)» **из видимой Activity** запускает настоящий started foreground Service. Он делает конечную полезную передачу данных через coroutine IO, поддерживает progress/cancel и сразу останавливается по завершении, отсутствии сети/необходимости входа либо отмене. Не держит сервис часами в ожидании сети. В уведомлении — прогресс, возврат в приложение и остановка. В UI — тот же статус из repository/Room через Flow; команды идут в Service, состояние возвращается через общее хранилище. Binding не обязателен; не хранить ссылку на Activity в Service.

Это лучше демонстрационного «пустого Service» и непрерывного GPS: реальный upload фото/заявок — разрешённый use case dataSync. Но FGS не следует включать ради любого миллисекундного запроса: маленькое обновление в открытом приложении может выполнять repository; Service предназначен для заметной, инициированной пользователем отправки, продолжающейся после Home. Искусственно замедлять production ради оправдания FGS не нужно. [Android: service types](https://developer.android.com/develop/background-work/services/fgs/service-types)

Ограничения, которые нельзя обойти обещаниями:

1. Обычный background started Service не является постоянным демоном: начиная с ограничений Android 8 система ограничивает его после ухода приложения в idle. После `startForegroundService` нужно быстро перейти в foreground с уведомлением; официальная документация Android 8 указывает пять секунд. Не делать сетевую работу до этой процедуры. Service сам по себе не отдельный рабочий поток: IO вынести в coroutine dispatcher. [Background execution limits](https://developer.android.com/about/versions/oreo/background)
2. На Android 12+ при target API 31+ запуск FGS из background запрещён, кроме специальных исключений. «Вернулась сеть» не является универсальным разрешением стартовать наш FGS. Не строить MVP на обходе исключениями: пользовательский запуск из видимого UI — простой основной путь. [Background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
3. Для target Android 14/API 34+ нужны корректный manifest type `dataSync`, обычное `FOREGROUND_SERVICE` и `FOREGROUND_SERVICE_DATA_SYNC`; Service не экспортировать без необходимости. Не приписывать dataSync право читать GPS/камеру: для while-in-use permissions существуют отдельные ограничения, на Android 14+ проверки возможны уже при создании соответствующего FGS. GPS и съёмка в этом MVP выполняются в видимом UI. [Service types](https://developer.android.com/develop/background-work/services/fgs/service-types), [restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)
4. На Android 15 при target API 35+ `dataSync` ограничен суммарно шестью часами за 24 часа для приложения; вывод приложения на передний план сбрасывает таймер по документации. Это потолок, не обещанная длительность жизни. Нужна обработка `Service.onTimeout(int,int)` с остановкой за несколько секунд; dataSync из BOOT_COMPLETED при target 35+ запрещён. В MVP передачи короткие, без автозапуска вечного сервиса при boot. [Target-35 changes](https://developer.android.com/about/versions/15/behavior-changes-15), [timeouts](https://developer.android.com/develop/background-work/services/fgs/timeout), [types](https://developer.android.com/develop/background-work/services/fgs/service-types)
5. Android 13/API 33+ имеет runtime `POST_NOTIFICATIONS`. Отказ не запрещает запуск FGS, но уведомление всё равно нужно предоставить; при отказе пользователь видит FGS в Task Manager, а не обычном notification drawer. Это локальное служебное уведомление — не исключённый из проекта push. [Notification permission](https://developer.android.com/develop/ui/views/notifications/notification-permission)
6. Пользователь может остановить FGS-приложение через Active apps/Task Manager начиная с Android 13; система останавливает весь процесс без callback. Это не то же самое, что Settings Force stop: документация отдельно говорит, что уже запланированные jobs/alarms после Task Manager Stop могут выполняться. Нельзя рассчитывать на onDestroy как на единственное место сохранения. [User stopping](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)
7. Если будет публикация в Google Play, тип FGS и его использование дополнительно декларируются и оцениваются по политике Play. Техническая допустимость OS не равна гарантии прохождения Play review. Для учебного APK это не причина расширять MVP. [Service types / Play policy](https://developer.android.com/develop/background-work/services/fgs/service-types)

### Что означает «синхронизация при закрытом приложении»

| Состояние | Реалистичное обещание MVP |
|---|---|
| Приложение открыто, сеть вернулась | Предложение: автоматически попытаться отправить pending в активной сессии, либо явная кнопка. Триггер должен быть согласован и проверен, а не только индикатор сети: сеть ≠ доступность API. |
| Нажат Home / экран погашен после явного запуска FGS | Уже запущенная конечная отправка может продолжаться с Service; нет гарантии завершения/срока. При остановке данные остаются для повторной отправки. |
| Back / swipe из Recents | Не равны универсально force-stop. Поведение зависит от lifecycle, настройки Service и OEM. Не обещать «всегда продолжится»; подтвердить на выбранном устройстве. Следующее открытие восстанавливает очередь. |
| Система убила процесс | Очередь/файлы уже сохранены; повтор при следующем допустимом запуске. `START_STICKY` не делает операцию вечной/надёжно доставленной. |
| Settings Force stop / `am force-stop` | Автоматическую синхронизацию до выхода из stopped-state действием пользователя не обещать. Самый понятный сценарий — открыть приложение, войти при необходимости и повторить sync. Android 15 также отменяет pending intents в stopped-state. [Stopped state](https://developer.android.com/about/versions/15/behavior-changes-all) |
| Reboot | Сохранённые локальные данные остаются; основной MVP восстанавливает при открытии. Не запускать dataSync FGS из boot receiver на target 35+. |
| Сервер недоступен, Doze/экономия/OEM ограничения | Нет гарантированного дедлайна/доставки; виден pending и последняя ошибка, повтор безопасен. |

WorkManager можно **опционально** добавить для отложенных подходящих попыток при сети, без обещания точного времени и без обхода force-stop; он не заменяет требуемый Android Service и не обязателен для первого рабочего вертикального среза. Формулировка для демонстрации: «Данные сохраняются локально; при активном приложении и доступном сервере выполняется sync, вручную запущенная отправка может продолжаться в фоне; после остановки приложения pending восстанавливается при следующем открытии». Если заказчик требует unattended eventual sync без открытия — это отдельное согласование механизма/ограничений, не гарантия FGS.

## 6. Оставшиеся blockers и риски

Бизнес-решения о demo accounts/одной роли, optional фото, GPS best effort, финальном CLOSED и явных конфликтах **утверждены**: повторно спрашивать их не нужно. CRUD/UUID/filesDir/app_logs/Outbox также обязательны, не варианты.

**Реальный blocker перед реализацией sync — короткий API/state contract архитектора:** формат close snapshot/revision, коды и UI-переходы после rejection/conflict, неизменяемость pending и способ выяснить исход неоднозначного close; photo upload/ref и ownership, идемпотентность и cleanup непривязанных uploads. Это одно согласование между исполнителями, не запрос новых enterprise-функций. При конфликте с серверным CLOSED не допускать повторного закрытия другой операцией. Если перечень обязательных checklist/reading полей ещё не задан, определить его в seeds/validation contract, не приписывать фото/GPS обязательность.

**Для финальной Android-приёмки** зафиксировать minSdk/targetSdk и фактическое OS/устройство; SDK не выдумывать. Точный logout UX и числовые значения retention/таймаутов можно зафиксировать безопасными документированными defaults, это не повод блокировать skeleton или повторно обсуждать все бизнес-решения.

Главные риски и проверки:
- Потери/дубли close: atomic Room+Outbox, immutable snapshot, atomic server dedup, T02–T06.
- Воскресание удалённого draft: stale callback/pending, разрыв DB/file cleanup, T16; close pending нельзя удалять «как черновик».
- Фото или private ref невалидны: filesDir, upload-before-close, auth/ownership для upload/download, T08/T10.
- Auth/PII: account-scoped cache/Outbox и безопасный общий logger; T07/T08/T15.
- Service «для галочки»/illegal background start: конечный user-initiated FGS, не вечный daemon; T12–T14. WorkManager лишь дополнение.
- Раздувание: один Android-клиент, Ktor, PostgreSQL и простой media volume; draft-only local CRUD, seeds заявок. Будущее create work_order допускается чистыми границами use case/repository, не нынешними endpoint/UI/ролями.

## 7. Короткий сценарий приёмки и статус проверки

1. Поднять backend по инструкции, войти, получить назначенную заявку.
2. Без сети заполнить работу, сделать фото/зафиксировать GPS либо показать согласованный fallback, сохранить/закрыть локально.
3. Убить процесс, открыть offline: работа и фото на месте.
4. Вернуть сеть, запустить sync и уйти Home: увидеть реальную работу Service; прервать ответ после commit и повторить.
5. Проверить сервер: одна работа, одно фото, один эффект закрытия. Вернуться в UI: актуальный статус. Показать auth 401/409 и landscape без потерь.
6. Отдельно force-stop, затем открыть: pending восстановлен, до открытия обещаний фонового sync нет.
