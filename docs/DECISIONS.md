# Согласованные решения первого этапа

Этот документ уточняет docs/TASK.md по результатам согласования с пользователем. CLAUDE.md остаётся без изменений. Полный API-контракт готовится отдельно; этот файл не означает завершённой реализации.

## Объём

Уровень B: Android Kotlin/Jetpack Compose/Room/Coroutines/Flow и REST-сервер Kotlin Ktor/PostgreSQL, локальный запуск через Docker Compose. Работа с предварительно загруженными данными без Интернета, последующая синхронизация, авторизация. Без push, непрерывного GPS и сложного автоматического слияния конфликтов.

## Данные и CRUD

- Для идентификаторов всех сущностей, операций очереди и событий журнала использовать UUID в строковом формате. Автоинкрементные числовые идентификаторы сущностей не использовать. Счётчики ревизий/попыток остаются числами, это не ID.
- Одна роль — инженер. Готовые демонстрационные аккаунты и заявки создаются на backend. Отдельную диспетчерскую панель и регистрацию в первом этапе не реализовывать.
- Мобильный клиент получает заявки и меняет допустимые статусы; не создаёт и не удаляет заявки.
- Полный CRUD демонстрируется на inspection_results: создать, прочитать, изменить и удалить локальный черновик до закрытия и синхронизации. Удаление черновика не должно приводить к его последующей отправке или восстановлению из старой операции.
- Закрытие окончательное; ожидающее отправки локальное закрытие и подтверждённое сервером закрытие явно различаются.
- Возможность будущего создания заявок обеспечить понятной схемой и разделением UI/логики/репозитория/API. Не добавлять неиспользуемые endpoints, скрытые кнопки или спекулятивные поля. В документации расширения описать будущие изменения. work_orders — единое имя сущности; tickets — синоним в обсуждении.

## Фото и GPS

- Фото необязательны. Binary хранится в приватной файловой системе Android, не BLOB в SQLite. Room хранит локальный путь и отдельную серверную ссылку/идентификатор.
- Сначала загрузить файлы на Ktor-сервер, затем отправить связанный результат закрытия. После upload не терять localPath; повторные запросы безопасны. Серверный доступ к фото авторизованный, не публичная раздача каталога.
- При закрытии в видимом UI автоматически запрашивать актуальную геопозицию. При отказе, недоступности или таймауте сохранять честную причину отсутствия, не блокировать сохранение/закрытие и не выдавать старую точку за текущую. Постоянного трекинга и фонового доступа к GPS нет.

## Outbox и Android Service

- Обязателен Outbox Pattern: бизнес-изменение и запись очереди сохраняются одной Room-транзакцией. Операции с UUID и состоянием переживают перезапуск, имеют безопасные повторы и серверную идемпотентность.
- Foreground Service типа dataSync реально выполняет последовательную отправку файлов и данных, показывает постоянное уведомление на время работы и обновляет UI через сохранённое состояние/Flow.
- Foreground Service НЕ гарантирует бессмертие процесса, точное время запуска или работу после force-stop. Учитывать ограничения Android, отмену, таймауты и восстановление очереди. Не стартовать FGS из произвольного фонового callback сети в обход ограничений.
- При восстановлении сети автоматическая попытка выполняется только разрешённым ОС способом; ручная кнопка запускает foreground-путь из видимого UI. WorkManager может дополнять, но не заменять требуемый Service.
- Конфликты разрешаются явно через UI: локальная работа сохраняется, сервер не перезаписывается молча. Никакого автоматического merge; можно явно принять серверную версию после просмотра локальной копии.

## Журналирование

- Обязательна локальная техническая таблица Room app_logs, UUID String для события.
- Простая обёртка пишет критические события синхронизации и ошибки в Logcat и app_logs. Ограничить рост журнала и не логировать пароли, токены, точные координаты, содержимое фото или комментарии инженера.
- Добавить технический экран просмотра логов для демонстрации. app_logs и outbox — служебные таблицы, они не заменяют 5–7 предметных связанных таблиц.

## Работа команды

Архитектор уточняет общий контракт, QA — критерии приёмки. Параллельная реализация Android и backend начинается по единой версии контракта. Изменения через ветки и pull request; merge в main только после одобрения пользователя. Успешная сборка/устройство заявляются только при фактически выполненных проверках.
